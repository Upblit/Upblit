# Security Standards

> Security requirements and observed security posture for the Upblit platform. All agents must follow these standards when generating or reviewing code.

---

## Authentication Architecture

### Current Implementation
- **Provider**: GitHub OAuth2 only
- **Flow**: Authorization Code Flow via Spring Security OAuth2 Client
- **Token**: JWT (JJWT 0.12.6) — signed with `JWT_SECRET` env var
- **Refresh**: Refresh tokens stored in PostgreSQL (`RefreshToken` entity)
- **Frontend storage**: JWT in `localStorage["token"]`

### JWT Security Rules
- `JWT_SECRET` must be at minimum 256 bits (32 bytes) of random entropy
- JWT must have an expiry (`exp` claim) — verify this is set in `JWTService`
- Refresh tokens must be single-use (invalidated after use)
- On logout: remove token from `localStorage` AND invalidate refresh token server-side

### OAuth2 Security Rules
- `REDIRECT_URI` must exactly match the registered callback in GitHub OAuth App settings
- `CustomOAuth2UserService` must validate the GitHub user response before creating/updating the local User record
- `OAuth2SuccessHandler` must not expose the JWT in the redirect URL query string — use a short-lived code or set via cookie/response body

## API Key Security

- API keys are generated by `ApiKeyGenerator` and stored in PostgreSQL (`ApiClient` table)
- API keys are used by SDKs via `x-api-key` header for ingest authentication
- **Frontend rule**: Generated API keys are displayed once in `ApiKeyModal` and never stored in `localStorage`, `sessionStorage`, or cookies
- **Backend rule**: Store only a hash of the API key, not the plaintext — verify this is implemented in `ApiKeyGenerator`
- API keys must be scoped to a single Application — not reusable across applications

## Authorization (RBAC)

### Current State
- `Plan` entity exists — suggests billing tiers
- `Invite` system exists for adding users to organizations
- No explicit RBAC role definitions found in the codebase

### Required Rules (Not Yet Implemented)
- Users should only access Organizations they belong to
- Users should only access Projects within their Organizations
- API key validation must verify the key belongs to an Application in an Organization the requesting user has access to
- Admin vs. member roles within an Organization should be enforced

---

## Input Validation

### Backend
- Use Spring Validation (`@Valid`, `@NotNull`, `@Size`) on all DTOs
- File uploads: validate MIME type and size server-side (not just client-side)
  - Current config: `spring.servlet.multipart.max-file-size=10MB`
  - Client-side limit is 5MB — backend allows 10MB — align these
- Never trust client-provided `organizationId` or `projectId` without verifying the authenticated user has access

### Frontend
- Form validation is client-side only — this is acceptable for UX but not for security
- Never interpolate user input into raw HTML (React JSX handles this)
- File type and size validation before upload: image only, max 5MB for logos

## Secrets Management

### Environment Variables (Required)
```
MONGODB_URI          — MongoDB Atlas connection string (contains credentials)
POSTGRES_URL         — PostgreSQL JDBC URL (contains credentials)
POSTGRES_USERNAME    — PostgreSQL username
POSTGRES_PASSWORD    — PostgreSQL password
GITHUB_CLIENT_ID     — GitHub OAuth App client ID
GITHUB_CLIENT_SECRET — GitHub OAuth App client secret
JWT_SECRET           — JWT signing secret (min 256-bit)
EMAIL_SECRET         — Email service authentication secret
SUPABASE_API_KEY     — Supabase service role key
```

### Rules
- Never commit `.env` files — `Upblit/backend/.env` is gitignored
- Never log secret values — log key names only
- Rotate secrets on suspected compromise
- Use separate secrets for development, staging, and production environments

---

## Transport Security

- All production traffic must use HTTPS
- The backend must set `Strict-Transport-Security` header in production
- CORS must be configured to allow only the known frontend origin (`FRONTEND_URI` env var)
- The `SecurityConfig` must not use `permitAll()` on sensitive endpoints

---

## File Upload Security

- Validate MIME type server-side using magic bytes, not just file extension
- Store files in Supabase (external storage) — not on the application server filesystem
- Generate random, non-guessable filenames for stored files
- Do not serve uploaded files directly from the backend — use Supabase's CDN URLs

## Known Security Gaps (Documented, Not Fixed)

| Gap | Risk | Priority |
|---|---|---|
| No explicit RBAC roles found | Users may access other orgs' data | Critical |
| API key storage format unknown | If stored in plaintext, a DB breach exposes all keys | High |
| JWT expiry not verified in this analysis | Tokens may not expire | High |
| No rate limiting on ingest endpoints | SDK abuse could cause storage exhaustion | High |
| No CORS config verified | May allow cross-origin requests from any domain | High |
| Client-side file validation only | Malicious files could bypass size/type limits | Medium |
| Refresh token single-use not verified | Token replay attacks possible | Medium |
| No audit log for API key generation | Cannot detect unauthorized key generation | Medium |
| `localStorage` token storage | Vulnerable to XSS (industry-standard tradeoff for SPAs) | Low (accepted) |
