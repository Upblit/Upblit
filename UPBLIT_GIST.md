# Upblit - Project Gist

Upblit is an open-source, cloud-native developer platform for building, deploying, monitoring, and scaling applications with less manual DevOps work. The workspace contains a full product ecosystem: a web dashboard, a Spring Boot backend, an AI/RAG service, an observability ingestion service, SDKs, a CLI, docs, policies, and supporting email/community assets.

## What It Does

Upblit aims to give developers a zero-config infrastructure experience:

- Deploy full-stack apps from GitHub, Docker, CLI, or API flows.
- Manage organizations, projects, applications, API keys, users, and tenants.
- Support authentication with OAuth2, JWT, refresh tokens, and Spring Security.
- Collect logs, traces, telemetry, and metrics for observability.
- Provide SDKs that applications can install to send request traces and logs.
- Add an AI/RAG layer for document upload, query answering, tenant isolation, guardrails, intent classification, and model routing.
- Offer documentation, Swagger/API pages, policies, onboarding emails, and community-facing pages.

## Agentic RAG: capabilities, tools, and exact integration surface

This project includes an agentic RAG mode implemented in `UpblitAI/` that can act as a constrained assistant and invoke a small, well-defined toolset. The following is the exact, minimal tool interface and how an evaluation agent should use it. Keep these constraints when giving the gist to another AI.

1) Tool: `ai.health_check`
	 - Source: `UpblitAI/Python/app.py` -> `GET /health`
	 - Purpose: quick liveness and readiness check
	 - Auth: API key enforced by `APIKeyMiddleware` (see `middleware/middleware.py`)
	 - Returns: JSON `{"status":"ok"}` or equivalent service-level diagnostics

2) Tool: `ai.query_rag`
	 - Source: `UpblitAI/Python/app.py` -> `POST /query`
	 - Purpose: submit user query for RAG processing. The request is queued to background workers (`services/worker.py`) and processed by `services/query.py` which:
		 - embeds the query (`HuggingFaceEmbeddings` in code)
		 - queries Qdrant (`config/db.py`) for top-K context
		 - invokes an LLM via `llmops.ModelRouter` when needed
		 - applies `llmops.guardrails` for input/output sanitization and safety
	 - Auth: API key required
	 - Response pattern: the endpoint enqueues the job and returns an acknowledgement; final results are produced by the async worker (the project uses internal task queues and worker processes; see `worker.py`).

3) Tool: `ai.add_document`
	 - Source: `POST /add_doc` -> controller in `controllers/add_doc.py` and services in `services/add_pdf.py`/`documents_chunks.py`
	 - Purpose: ingest documents, chunk, index into vector DB (Qdrant) and persist metadata to Supabase/tenant store
	 - Auth: API key required

4) Tool: `telemetry.ingest_trace` and `telemetry.ingest_log` (read-only counterparts exist for query)
	 - Source (ingest endpoints): `ingestor/main.go` -> `POST /ingest/upblit_traces`, `POST /ingest/upblit_logs`
	 - Purpose: ingest telemetry (write path). The ingestion service also runs workers that populate MongoDB collections `upblit_metrics`, `upblit_traces`, `upblit_logs` (see `main.go` in `ingestor/`).
	 - Important: agentic RAG MUST NOT call ingest endpoints to write data unless explicitly allowed by policy; the agent should use the read/query interfaces described next.

5) Tool: `telemetry.query` (read-only)
	 - Implementation surface: the backend `query` and `ai` modules plus `ingestor/` stored MongoDB collections are the canonical sources for telemetry. For machine-driven evaluation, the following read strategies are supported:
		 - Direct HTTP read endpoints (if present) in the backend that perform aggregated telemetry queries. Inspect `backend/src/` for `query` or `observability` controllers to find exact route names.
		 - Direct DB access by a privileged tool (NOT recommended for external agents) to `observability.upblit_traces`, `observability.upblit_logs`, and `observability.upblit_metrics` in MongoDB.
	 - Recommendation: implement or use a dedicated backend read-only endpoint (e.g., `/api/internal/telemetry/query`) that accepts tenant-scoped parameters and returns sanitized JSON — this is the expected interface for `telemetry.query` calls.

6) Tool: `uptime.check` (pinger)
	 - Source: `pinger/` application (see `pinger/main.go` and `internal/` code)
	 - Purpose: run scheduled pings, synthesize uptime percentages, and expose health checks for apps or the platform
	 - Interface: `pinger` exposes internal APIs and stores heartbeat/uptime records; agentic RAG should call a backend read endpoint that summarizes uptime (the repo contains pinger code but the exact HTTP summary endpoint is implemented under `pinger/internal/httpapi` — inspect there to map to a URL). If no summary endpoint exists, create one that reads from the pinger store.

7) Tool authorization and guardrails (critical):
	 - Every tool call must present an API key scoped to the tenant and to read-only permissions unless explicit write is required.
	 - Rate limiting and request quotas must be enforced by `APIKeyMiddleware` or a gateway layer.
	 - The agent's returned outputs must be validated via `llmops.guardrails.validate_llm_output` before being surfaced to users.

## How to run and enable agentic mode (practical steps)

1) Start infrastructural dependencies (example):
```bash
cd Upblit/infrastructure
docker compose -f docker-compose.java-redis.yml up -d
docker compose -f docker-compose.ingestor.yml up -d
```

2) Start the ingestor (local dev):
```bash
cd Upblit/ingestor
go run main.go
```

3) Start the AI service (agentic RAG):
```bash
cd UpblitAI/Python
python -m venv .venv
.venv\Scripts\activate   # Windows
pip install -r Requirements.txt
uvicorn app:app --reload --port 8001
```

4) Configure `UpblitAI` for agentic operation:
	- Populate `.env` in `UpblitAI/Python/` with `QDRANT_URL`, `QDRANT_API_KEY`, `SUPABASE_*`, and any model provider keys.
	- `config/config.yaml` controls model routing and tiers. Use it to enable conservative routing for agentic operations (prefer smaller/cheaper models for queries that only need short answers).
	- Ensure `APIKeyMiddleware` is configured and that the agent is issued a read-only API key scoped to telemetry and vector search.

5) Example: run a RAG query (agentic flow):
```bash
curl -X POST https://<upblit-ai-host>:8001/query \
	-H "Authorization: ApiKey <read-only-key>" \
	-H "Content-Type: application/json" \
	-d '{"job_id":"job-1234","tenant_id":"tenant-abc","query":"What is the uptime for app X in the last 7 days?","prompt":"Answer concisely using only verified telemetry data."}'
```

## Security & safety checklist for an AI evaluating this repo

- Always prefer read-only HTTP endpoints that sanitize and redact PII.
- Ensure `APIKeyMiddleware` is active for `UpblitAI` and `ingestor` endpoints.
- Agent must not request raw DB credentials or direct DB reads unless explicitly authorized and audited.
- Limit agent actions to: `ai.health_check`, `ai.query_rag`, `ai.add_document` (ingest), `telemetry.query` (read-only), and `uptime.check`.

### AI/RAG Service

- `GET /health`
- `POST /query`

### Observability Ingestor

Located in `UpblitIngestor/`.

This is a Go service built with Gin. It receives trace and log ingestion requests, validates API keys, publishes and consumes telemetry through Kafka, aggregates data, converts traces/logs, and stores observability data in MongoDB collections for metrics, traces, and logs.

Core endpoints include:

- `GET /health`
- `POST /ingest/traces`
- `POST /ingest/logs`

### SDKs

Located in `SDK/`.

The workspace includes SDKs for multiple application stacks:

- `Express-sdk/`: Express middleware for request tracing, log collection, span helpers, health route, batching, and ingestion delivery.

- `Python-sdk/`: Python SDK with middleware, context, transport, SDK types, and tests.
